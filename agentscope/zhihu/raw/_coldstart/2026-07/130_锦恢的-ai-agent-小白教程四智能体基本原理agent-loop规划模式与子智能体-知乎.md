所以到底什么是 agent harness？也就是在 ReAct 这个层级对工具，架构，任务执行方式，调度策略基于你的实际业务来进行对应的设计、开发和后续的优化。如果我们将大模型的神奇能力比作CPU那一秒上一次运算的强大计算能力。那么 agent harness 其实就类似于操作系统的设计与开发。毕竟，操作系统本身的设计与开发并没有从物理层面来增加 CPU 本身的运作效率，但是它却行之有效的让人类能够更好的驾驭 CPU。
我举个例子，比如说让我们的智能体在执行某一个任务的过程中，顺带让它将一个文档进行观测和总结，是一个很常见的需求。但如果我们直接的让智能体总结文档，它会直接调用相关的工具，来将一整份文档里面的文本载入整个上下文。不少的文档可能都有100多页10万字，那么可能就直接会占据对应大模型40%的上下文，让之前的任务的执行，直接在后续因为上下文爆炸了失败，或者提前进入压缩上下文，降低使用的体验和成功率。那么这个时候一个优秀的 harness/loop engineering 工程师就应该想到，可以通过调试系统提示词来执行对应的 Agentic RL，并使用 subagent 的方法，让对应的大模型驱动的智能体，面对这样的一类任务时，能够直接将任务开在一个子智能体里面，并直接获取最终的结果，从而完成上下文的隔离。让文档总结这一个任务，不会让上下文爆炸。而像这样的 corner case，在整个 agent 的实际业务开发中有很多很多。
所以通过这个例子，你也能看到，在实际的工业场景的开发中，我们发现 agent harness 和 model training 并不是完全解耦合的，它们之间仍然有一些相关的地方。
比如我们上面提到的让 AI 尽可能将文档总结这类任务来开成子智能体，这不仅仅需要对系统提示词进行一定的优化，甚至有的时候还需要来对大模型做对应的 Agentic RL 的训练，来让它记住这类任务，尽可能开子智能体。
这个其实就和人类在执行一些任务的时候一样，我们只是修改系统提示词的话，它也只是临时的记住一个指令，而进行训练，则是养成对应的肌肉记忆。
显然，一个长期迭代的能够成为业务扛把子的智能体，它一定是需要像人一样在睡眠的时间，加固某些记忆，形成一些业务上的肌肉记忆的。
所以从长期来看，一个优秀的智能体的开发中，Agentic RL 训练是不可避免的一件事情。
锦恢仍然认为，目前的 AI Agent 的架构设计和开发处于一个早期阶段。
