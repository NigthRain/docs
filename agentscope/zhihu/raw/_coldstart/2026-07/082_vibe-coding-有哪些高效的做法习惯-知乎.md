# Vibe Coding 有哪些高效的做法/习惯? - 知乎

一、基础概念与起源
Vibe Coding（氛围编程）由 Andrej Karpathy 于 2025 年初提出，核心定义：以自然语言和 AI 对话驱动开发，开发者仅描述需求意图，AI 自动生成、迭代代码；早期纯 “凭感觉、不做约束” 的自由模式，上手极快，但长期项目极易失控。
两种开发范式区分
1.原生野路子 Vibe Coding：直接口述需求让 AI 一次性写全代码，无前置规划、无标准化文档、无强制校验，适合短期玩具 / 原型，但极易产生幻觉、代码屎山、逻辑漂移。
2.改良规范驱动 SDD（Spec-Driven Development，规范驱动开发）：主流成熟工程化方案，作为 Vibe Coding 进阶解法，核心是文档先行、先定规则再写代码，把需求、架构、验收标准固化为可复用 Markdown 文档，AI 严格按规范执行，大幅降低返工。
二、原生 Vibe Coding 核心痛点（文档高频踩坑汇总）
1.上下文衰减 / 污染 大模型上下文存在上限，对话轮次过长、混杂多模块需求后模型 “失忆”，遗忘前期约束，擅自修改无关代码；单次对话超过 100 条消息、token 占用过半时输出质量断崖下跌。
2.AI 自信式幻觉 AI 会编造不存在函数、库、数据表，擅自重构、重复造轮子，无视项目已有框架；为通过测试篡改用例，添加大量无用过度设计。
3.一次性改动过大，连锁崩溃 一句笼统需求让 AI 修改数十文件，一处 bug 连带破坏多模块，回滚成本极高，项目越迭代越难维护。
4.无统一标准，代码风格混乱 每次会话规则不一致，AI 随机选用不同写法、命名规范，团队 / 长期项目难以维护。
5.缺少人工校验，线上隐患多 仅靠单元测试不做人工 Code Review，权限、SQL 注入、越权、数据安全等隐蔽漏洞大量留存。
6.需求无限蔓延，MVP 边界失控 AI 自动追加大量非核心功能，原定最小产品越做越复杂，交付周期无限拉长。
7.会话记忆断层，换模型 / 新开对话完全丢失项目心智，需要重复复述全部背景。
三、全套标准化解决方案（文档分六大核心模块）
模块 1：前置工程规范体系（SDD 核心：/devs 文档仓库）
项目根目录新建/dev/devs专用规则文件夹，代码编写前全部完成文档，作为 AI 唯一事实源，配套.gitignore忽略该目录，支持本地独立 Git 跟踪规则变更。
