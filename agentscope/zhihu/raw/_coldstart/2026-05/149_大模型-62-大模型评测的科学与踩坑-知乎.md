虽然 Loss 和压缩率能够衡量模型对语料库的适配程度。然而，较低压缩率并不直接等同于模型在具体任务上具备更高的禀赋。因此，我们需要在预训练阶段引入 Benchmark，通过具体任务来试图量化能力，从而获取模型的表现。
・评测通常会在输入中添加 Few-shot，以确保模型提供的示例与目标格式保持一致。同时可以在 few-shot 中加入 cot，测试 pretrain model 的 thinking 能力。
・同时 Few-shot 存在明显局限，例如模型可能会受到 Shot 内容分布的影响或者引导性弱。因此，另一种评估方式是基于 Perplexity（困惑度），但这种方法仅适用于答案固定且简短的客观题。
・对于代码生成等任务，采用 Fill-in-the-Middle（FIM）模式进行预训练评测，通过引导让模型在程序中填空，再通过测试用例进行评分。
3. 预训练阶段的监控指标选择
在预训练阶段，如何通过监控合适的指标，来检验模型在未来的表现。这种相关性很大程度上是基于直觉的判断。针对这一问题的可能解决方法（抛砖引玉讨论性质，仅供参考）：
持续监测一致的 Benchmark：
对于很多能力类指标，在预训练阶段往往难以有效监控。其核心瓶颈在于模型此时尚缺失指令遵循能力，且上下文较短等。并且部分 Benchmark 的指令引导性较弱，即使通过 Few-shot 引导，基座模型仍难以产生有效的遵循行为，所以应该筛选出一个适合监控的指标 list。
可在预训练阶段有效监控的：
单选题类 benchmark（MMLU / CEVAL / FinEval / AGIEval 等），通过 few-shot + 续写截断即可获取稳定信号；BBH 类推理题也可通过 few-shot 引导格式化输出。
难以在预训练阶段有效监控的：
需要指令遵循的对齐类评测（AlignBench）、需要多轮交互的评测（MTBench）、需要 LLM Judge 的开放式评测、以及需要长上下文 + 复杂输出解析的 Coding 评测（LiveCodeBench）、Agent 能力类的评测。这些能力类指标依赖后训练赋予的指令遵循能力。
在预训练阶段仅监控极少数通用指标：
以防止训练崩溃，主要通过 Loss 和压缩率来评估模型性能的基础水位，而不对具体能力做过多干预。
